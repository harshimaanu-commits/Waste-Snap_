WasteSnap: the complete beginner's guide

What the project does, how every file fits together, and how data moves from a button click all the way to the database and back. No prior Flask or MongoDB knowledge needed.

1The big picture

WasteSnap is a website where people report waste problems (garbage piles, overflowing bins, illegal dumping) and the city handles them.

Think of it as a small ticket system for waste. A complaint is a ticket. It starts when a citizen reports a problem with a photo, and it ends when it is cleaned up and the proof photo is checked. Four kinds of users take part:

Citizen

Signs up on the website. Reports problems with a photo and says how many days the problem has existed (a counter that grows every day). Follows each report, and rates the cleanup once it is resolved.

Admin

The manager. Checks (verifies) new reports, assigns them to a worker, and resolves them once the work is proved. Also pays companies.

Worker

Does the cleaning. Sees only the tasks given to them, starts the work, and uploads an "after" photo. Has 7 days per job; finishing late costs ₹50.

Company

A contractor. After a complaint is resolved, the admin creates a payment for the company. The company sees what it is owed or has been paid.

It is a demo. Payments are just records in the database (no real money moves) and the project is built to be understandable, not to handle a whole city. Section 12 lists what a real product would add.

2The technologies, in plain words

Everything the project is built from. Each one solves one small problem.

Python

The programming language the whole back end is written in.

Flask

A small Python library that turns functions into web pages. You write def login(), tell Flask "run this when someone visits /login", and it handles the web part.

Jinja templates

HTML files with blanks in them, like Hello, {{ current_user.name }}. Flask fills the blanks before sending the page to the browser.

Blueprints

Flask's way to split many routes into separate files (auth.py, admin.py...) so one file does not become huge.

Flask-Login

Remembers who is logged in using a cookie, and provides @login_required and current_user.

MongoDB Atlas

The database, hosted in the cloud, so you and your friend share the same data from different laptops.

pymongo

The Python library that talks to MongoDB.

Werkzeug

Comes with Flask. We use it to turn passwords into scrambled "hashes" so real passwords are never stored.

python-dotenv

Reads secret settings (like the database password) from a .env file so they never go into the code or GitHub.

HTML, CSS, a little JavaScript

The pages you see. CSS (from your friend's design) makes them green and pretty. JavaScript is only used for the show/hide password eye and the photo preview.

3How the pieces work together

Every click follows the same path. Learn this once and the whole project makes sense.

The life of one request

Say the admin clicks Verify on a complaint:

  1. The browser sends a request: POST /admin/verify/6520ab...
  2. Flask finds the matching function in routes/admin.py. It checks the user is logged in and is an admin.
  3. The route asks db_helpers.py: "verify complaint 6520ab...".
  4. The helper sends one instruction to MongoDB Atlas: "if this complaint's status is Submitted, change it to Verified".
  5. MongoDB replies whether it changed anything. The helper returns True or False.
  6. The route shows a green or yellow message and redirects to /admin. That request runs again, the page is built from a template filled with fresh data, and the browser shows the updated table.

Why this split? Routes never touch the database directly and templates never contain database code. Each file does one job, so a change in one place rarely breaks another.

5Code walkthrough

The important parts of each file, in the order they run.

1. Startup: app.py

When you run python app.py, this happens in order:

  1. Create the app and load settings from config.py.
  2. Connect to MongoDB with init_db_connection(app). If MONGODB_URI is missing, it stops with a clear message.
  3. Set up Flask-Login. It needs a "user loader": given the id stored in the session cookie, fetch that user from the database.
  4. Register the blueprints (auth, complaints, admin, workers, company), which switches on all their URLs.
  5. Define three routes of its own: / (landing page), /dashboard/<role> (send each person to the right dashboard), and /db-check (admin-only database test).
@app.route("/dashboard/<role>")
@login_required
def dashboard(role):
    if role != current_user.role:     # a citizen cannot open /dashboard/admin
        abort(403)
    if role == "admin":
        return redirect(url_for("admin.dashboard"))
    ...

2. Settings: config.py

Reads .env and exposes SECRET_KEY (signs login cookies), MONGODB_URI, MONGODB_DATABASE, and DEBUG. The code never contains a password. That is why the project can safely live on GitHub.

3. Connection and users: models.py

  • init_db_connection(app) creates the MongoDB client once at startup.
  • get_db() gives other files the database object.
  • to_object_id(text) converts the text id from a URL into a MongoDB ObjectId, and returns None if the text is not valid, so a junk URL cannot crash the app.
  • User wraps a database record into an object with .id, .name, .email, .role, which is what Flask-Login expects.

4. The data layer: db_helpers.py

The main groups of functions:

GroupFunctionsWhat they do
Usersget_user_by_email, get_user_by_id, create_user, create_citizenFind or create accounts. Passwords are hashed before saving.
Complaints (read)get_complaints_by_user, get_all_complaints, get_worker_complaints, get_resolved_complaints_by_userFetch lists for each dashboard. The admin list also looks up the citizen's and worker's names.
Complaints (change)create_complaint, verify_complaint, assign_complaint, start_work_on_complaint, mark_work_done, resolve_complaintMove a complaint one step forward. Each returns True or False.
Companies and paymentsget_companies, get_resolved_without_payment, create_payment, mark_payment_paid, get_paymentsEverything for section 9.

The key idea is in how a status change is made. Instead of "read the complaint, check it, then save it" (which can go wrong if two people click at once), it sends one instruction that includes the rule:

def verify_complaint(complaint_id):
    ...
    # "find a complaint with this id AND status Submitted, set status to Verified"
    return _move_complaint(
        {"_id": object_id, "status": "Submitted"},
        {"status": "Verified"}
    )

If the complaint is not Submitted (already verified, or the id is wrong), nothing matches and the function returns False. This is why a complaint can never skip a stage.

6. Templates and the shared frame

Pages do not repeat the navbar and footer. Each page says "I build on base.html" and fills one empty slot:

Inside a template, {{ ... }} prints a value, and {% ... %} is logic (if, for). For example, the admin table shows a different button depending on the complaint's status:

{% if complaint.status == "Submitted" %}
    <button>Verify</button>
{% elif complaint.status == "Verified" %}
    ... a worker drop-down and an Assign button ...
{% endif %}

The login and register pages use auth_base.html instead, because they have the split-screen layout without the navbar.

7. Photo uploads

  1. The form uses enctype="multipart/form-data" so the browser can send a file.
  2. The route checks the file is present and is a .jpg, .jpeg, .png or .webp (secure_filename cleans the name).
  3. The file is saved in static/uploads/ under a random name (uuid4().hex plus the extension), so two uploads can never clash and a user cannot choose a dangerous file name.
  4. Only the file name goes into the database. Pages show it with <img src="/static/uploads/NAME">.
  5. If the database update fails after a worker uploaded a proof photo, the file is deleted again, so no orphan photos are left behind.

6The database

MongoDB stores documents (like small JSON objects) in collections (like folders of documents). WasteSnap has three collections.

  • One users collection for everyone. The role field decides what a person can do.
  • Photos are not in the database. Only file names are stored. The pictures live in static/uploads/.
  • A fourth collection, violations, is a log of strikes and warnings, written by log_violation() and read on the admin's Reviews page.
  • Indexes (created by init_db.py): users.email is unique (no duplicate accounts), and payments.complaint_id is unique (one complaint can be paid only once).
  • ObjectId: MongoDB's auto-generated id, a 24-character string like 65f1c2.... Pages show only the last 6 characters (#e8d914) to keep them short.

7The complaint lifecycle

The core of the project: a complaint moves through five stages, and each move can only be made by the right person.

Deadlines, ratings and the days counter

Worker deadline

When the admin assigns a complaint, deadline is set to 7 days later. Dashboards show "N days left" or "Overdue". If the worker uploads the proof photo after the deadline, was_late becomes true.

₹50 penalty

When the admin creates the payment for a late job, ₹50 is taken off: net_amount = amount - 50. The admin sees the warning first, and the company sees the deduction.

Rating

After a complaint is Resolved, its citizen can give 1 to 5 stars and an optional comment, once. The database update only matches if no rating exists yet, so a second try is refused.

Days existing

The citizen enters the days already passed. Each time a page loads, the app adds the days since the report was created, so the number rises by one daily. It stops at the resolved date.

# db_helpers.py: the counter is worked out on the fly, not stored
existing_days = days_existing + (end_time.date() - created_at.date()).days

Rules that keep the system fair

Beyond the deadline and the ₹50 penalty, there are rules for every role. Each is a small function in db_helpers.py, with the numbers kept as constants at the top of that file.

RuleApplies toWhat happens
Low-rating penalty reviewWorker (admin decides)A 1-2 star rating creates a pending review. It does not cut pay by itself. The admin sees the comment and the worker's timing and clicks Approve (₹25 off the job's payment) or Dismiss. The payment cannot be paid while a review is pending.
Not started in timeWorkerStill "Assigned" after 48 hours: a warning appears for the worker and the admin. No money.
Duplicate proof photoWorkerEach photo is fingerprinted (SHA-256). A proof photo that matches the citizen's photo, another job's proof, or an old rejected proof is refused and logged.
Database copy in filesAdmin / teacherAfter every successful change, the app waits 2 seconds (so many changes are written once) and rewrites data/json/*.json and data/wastesnap_backup.db. Admins can see and download them on the Data page. It is a one-way copy; MongoDB stays the real database.
Reject the worker's workAdmin and workerWhen a job is marked done, the admin can Resolve or Reject work with a reason. It goes back to the same worker with a new 3-day deadline, the rejected photo is blocked from re-upload, and it is logged against the worker. A job that was already late stays late.
Reopen a complaintCitizen and workerWithin 3 days, once, before rating, and before the payment is paid: back to In Progress with a new 3-day deadline. The payment goes on_hold and the reopen is logged against the worker.
Invalid or fake complaintCitizenThe admin rejects it. Invalid gives a strike; duplicate does not. 3 strikes in 90 days pause reporting.
Duplicate reportCitizenSame type and place within 7 days: refused for the same citizen; flagged for the admin if it was someone else's.

Why the admin has the final say on ratings: a citizen can give 1 star for no good reason. Automatic pay cuts would then punish a worker who did everything right. The review step puts a human between the rating and the money.

Every strike and violation is saved in a violations collection, shown on the admin's Reviews page.

8Login and security basics

What happens when someone signs in, and why the passwords are safe.

Password hashing

generate_password_hash("secret123") turns the password into a long scrambled string. Only that is stored. Even someone with database access cannot read the original password. Login re-scrambles what you typed and compares.

Sessions

After login, Flask-Login puts your user id in a cookie signed with SECRET_KEY. Nobody can forge it without the key.

Role checks

Every protected route starts with @login_required and a check like if current_user.role != "admin": abort(403).

Secrets stay out of git

.env is in .gitignore. Only .env.example (with placeholders) is committed.

Safe sign-up

Anyone who registers is always a citizen. Admin, worker and company accounts can only be created by running the create scripts on the computer.

Logout is a POST

It is a button inside a form, not a plain link, so another website cannot log you out by loading an image.

9Companies and payments

After a complaint is resolved, a company is paid for the work. The payment goes through a simulated gateway that behaves like a real checkout: you pick a method, watch the steps happen live, and get a receipt. No real money moves.

What the admin and the company see

  1. Request: on its dashboard the company enters an amount and a note for a resolved job. The request appears on the admin's Payments page.
  2. Approve or reject: the admin approves (the amount can be changed; penalties are worked out again) or rejects with a reason. A rejected request can be sent again.
  3. Pay now: the checkout shows the summary and penalty lines. The admin picks UPI, Bank transfer or Card and enters details. Demo buttons fill in working or failing test values.
  4. Live progress: five steps (initiate, verify payee, authorise with the bank, transfer, confirm). The page asks the server for the status every second and shows a progress bar and a timeline. The company can open the same screen, and its dashboard refreshes by itself when the payment ends.
  5. Success or failure: success gives a transaction ID and a printable receipt. A failure shows the reason, and the admin clicks Retry payment. Every attempt stays in the timeline.

How the simulation works

  • One atomic switch: start_payment() changes pending or failed to processing in a single database step, so two clicks cannot pay twice.
  • A background thread then moves the payment through the stages, waiting a little at each one and saving a timeline event (payment_gateway.py).
  • The live page polls /payments/<id>/status, which returns JSON. This is simpler than websockets and works the same on Windows and Mac.
  • Test values decide the outcome: for example PIN 0000, card 4000 0000 0000 0002, or an account number ending 0000 fails on purpose.
  • Safety: card numbers, PINs and CVVs are never saved (only "Visa card ending 1111"). A payment cannot be paid while a low-rating review is pending or the complaint is reopened. A payment stuck in processing (for example the server restarted) is marked failed so it can be retried.
  • Amounts: must be above 0 and at most 1,000,000, and larger than any penalty. amount, penalty and net_amount are all kept, and a unique index allows one payment per complaint.

10What we did, end to end

The project started as two separate versions and was combined into one.

Your version

A solid backend: real login sessions, roles, the five-stage workflow, proof photos. But it used MySQL, had a very plain Bootstrap look, and no company features.

Friend's version

A beautiful front end (landing page, login screens) and a MongoDB database. But login only lived in the browser, anyone could call the API to delete complaints, and there was no real workflow.

Combined

Your secure backend and workflow, the friend's design and MongoDB, and the new company and payments feature.

The steps

  1. Compared the two versions feature by feature: stack, security, workflow, data model, user interface.
  2. Chose the approach. Keep Flask with server-side pages and sessions (not a JSON API), use MongoDB Atlas, keep the five-stage workflow, add company payments (Option B: the admin pays a company for resolved work).
  3. Phase 1, the database. Replaced MySQL/SQLAlchemy with pymongo. Kept the same function and field names so the routes and templates barely changed. Moved settings to .env. Made status changes single conditional updates.
  4. Phase 2, the front end. Copied the friend's stylesheet, turned the landing page and login/register screens into Jinja templates, built the shared base.html, and redesigned the four dashboards to match.
  5. Phase 3, company and payments. Added the company role, the payments collection, the admin payments page, and the company dashboard.
  6. Phase 4, polish. Demo data script, README, AI setup file, line-ending settings, one password rule (8+ characters), an admin-only /db-check, and debug mode controlled from .env.
  7. Second round of features. Added the worker deadline (7 days) with a ₹50 penalty on the payment, citizen ratings and feedback, and the "days existing" counter.
  8. Third round: rules and fairness. Low-rating penalty with an admin review, not-started warnings, duplicate proof-photo detection, invalid-complaint strikes, duplicate-report and daily-limit checks, reopening, and an admin response-time alert. All covered by an automated test of more than 100 checks.
  9. Payment demo. Replaced the one-click "Mark as paid" with a simulated gateway: UPI, bank transfer and card, a live five-step progress screen, deliberate failures with retry, printable receipts, and company payment requests that the admin approves or rejects.
  10. Tested the whole flow with an automated script against a fake in-memory MongoDB (30 checks), looked at the pages in a browser, then you ran it yourself and pushed it to GitHub.

12Limits and ideas for next steps

Being honest about the limits is part of a good demo.

Limitation Photos

They are saved on the computer that ran the upload. Another laptop shares the database but does not have the image files.

Limitation No CSRF protection

A real site adds hidden tokens to every form (Flask-WTF) so other sites cannot trick a logged-in user into submitting one.

Limitation Simulated payments

No payment gateway. Payments are just records. The ₹50 penalty is taken off the job's payment, since workers do not have a separate salary in this demo.

Limitation No password reset

Or email verification, or rate limiting on login.

Easy ideas to extend it:

  • Store photos in cloud storage (for example Cloudinary or S3) so all laptops see them.
  • Add a map or GPS location instead of typing the address.
  • Let the admin reject a complaint with a reason.
  • Add charts on the admin page (complaints per week, average time to resolve).
  • Send an email when a complaint is resolved.
  • Add pagination when the lists get long.
